Write your own code: plain C and beitlabduino

Your program runs on the Duo S's C906 core under FreeRTOS. You can write it in two styles that build, upload and run the same way: plain C with FreeRTOS tasks, or beitlabduino, a thin setup()/loop() layer on top of the same runtime. Both work on the Robotics Board and on a standalone Milk-V Duo S. Only the hardware profile changes.

C11, riscv64 lp64dFreeRTOS, 5 ms tickPlatformIOSame code path on both platforms

Before you start, flash the board and run hello once, so you know the build and upload loop works.

1. Create a project

A project is a folder next to the examples. It must live inside examples/platformio/ because its platformio.ini loads the shared platform from ../common.

  1. Copy a starting point 
    $ cd duo-s-playground/examples/platformio
$ cp -r hello my_app                        # plain C; use beitlabduino_blink for the setup()/loop() style
  2. Edit my_app/platformio.iniThe environment name becomes the program name, and the profile decides the pins. Use one of these: 
    # Standalone Milk-V Duo S, plain C
[platformio]
extra_configs = ../common/playground.ini
default_envs = my_app

[env:my_app]
extends = playground
custom_profile = duos_bare

# Standalone Milk-V Duo S, beitlabduino
[env:my_app]
extends = playground
custom_profile = duos_bare
custom_libs = beitlabduino

# Robotics Board, plain C or beitlabduino (add custom_libs for the latter)
[env:my_app]
extends = playground
custom_profile = beitlab_robotics_rev011
custom_libs = beitlabduino
  3. Write my_app/src/main.cEvery .c and .S file under src/ is compiled, in subfolders too. Use the templates below.
  4. Build, upload, watch 
    $ cd my_app
$ pio run                       # compile only
$ pio run -t upload            # upload over SSH and restart the C906
$ pio run -t rtmonitor         # C906 log; Ctrl-C leaves the program running
    Set PIO_DUO_HOST if your board is not beitlab-milkv-duo.local. On the Robotics Board, unlock first with the E-stop open (carrier note).
Profile and platform must match

duos_bare is for a Duo S with nothing attached to the carrier. Never upload a program built with it to a Duo S fitted on the Robotics Board: it can grant access to pads that drive the motor enable and other robot connections. For the carrier, keep beitlab_robotics_rev011, which refuses everything the robot owns and allows only the on-board LED (A29). A profile that is empty or unknown fails the build.

2. Plain C template

A program is a set of FreeRTOS tasks created from playground_app_init(). The runtime calls that function once before the scheduler starts, so create tasks and queues there and return quickly.

/* my_app: blink the on-board LED and print a counter, in plain C. */
#include <stdint.h>              /* first: the SDK FreeRTOS.h does not include it */
#include "FreeRTOS.h"
#include "task.h"
#include "playground.h"          /* pg_print, pg_cmd_subscribe, pg_cmd_reply */
#include "pg_gpio.h"             /* pg_gpio_output, pg_gpio_write */

#define LED "A29"                /* Duo S on-board LED, allowed by both profiles */

static void blink_task(void *arg)
{
	int level = 0, count = 0;

	(void)arg;
	if (pg_gpio_output(LED)) {   /* -1: the profile refused the pad; it says why */
		vTaskDelete(NULL);
		return;
	}
	pg_print("my_app profile %s", pg_profile_name());
	for (;;) {
		level = !level;
		(void)pg_gpio_write(LED, level);
		if (level)
			pg_print("blink %d", ++count);
		vTaskDelay(pdMS_TO_TICKS(500));
	}
}

void playground_app_init(void)
{
	xTaskCreate(blink_task, "blink", configMINIMAL_STACK_SIZE, NULL,
		    tskIDLE_PRIORITY + 1, NULL);
}

Rules for plain C:

  • Include <stdint.h> before FreeRTOS.h. The vendor header does not include it.
  • Always block. A task must call vTaskDelay(), wait on a queue or semaphore, or delete itself. A task that never waits starves the idle task.
  • Print from tasks only. pg_print() is safe in tasks and not in interrupt handlers. It adds a newline, cuts lines at 160 characters, and writes to the serial console with an RT: prefix and to the log that rtmonitor reads.
  • Check before you touch hardware. pg_gpio_output() and pg_gpio_write() return 0 or -1 and check the profile first. To ask without side effects use pg_profile_gpio_output(pad, NULL) (returns NULL when allowed, otherwise the reason), pg_profile_resource(name) for peripherals and pg_profile_i2c_address(bus, address) for I²C devices.
  • Pad names are a port letter and a bit number, for example "A29". "B019" means the same pad as "B19". Only ports A to D are supported, and the pad must already be muxed to GPIO: the API never changes pinmux.

Receiving commands from Linux in plain C

Linux on the A53 can send the C906 an 8-byte mailbox message: a command id and a 32-bit value. Subscribe to an id, wait on the returned queue and reply once to each message. Ids 0x00 to 0x4f are yours, except 0x40 which the runtime keeps for ping; at most four can be subscribed. An id nobody subscribes to is echoed back unchanged.

#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"
#include "playground.h"

#define CMD_DOUBLE 0x45

static QueueHandle_t cmd_queue;

static void cmd_task(void *arg)
{
	cmdqu_t cmd;

	(void)arg;
	for (;;) {
		if (xQueueReceive(cmd_queue, &cmd, portMAX_DELAY) != pdTRUE)
			continue;
		pg_print("cmd 0x%x value %d", cmd.cmd_id, (int)cmd.param_ptr);
		pg_cmd_reply(&cmd, cmd.param_ptr * 2);    /* one reply per command, soon */
	}
}

void playground_app_init(void)
{
	cmd_queue = pg_cmd_subscribe(CMD_DOUBLE);
	xTaskCreate(cmd_task, "cmd", configMINIMAL_STACK_SIZE, NULL,
		    tskIDLE_PRIORITY + 2, NULL);
}

Send it from the PC with bl_send (installed on the board in image 0.4.1), as in the mailbox example: ./bl_send.sh 0x45 21 prints 42.

3. beitlabduino template

With custom_libs = beitlabduino, include beitlabduino.h and define setup() and loop(). Do not define playground_app_init(): beitlabduino provides it and calls your two functions from one FreeRTOS task.

/* my_app: the same program, Arduino style. */
#include "beitlabduino.h"

static int count;

void setup(void)
{
	bl_pin_mode(BL_LED, BL_OUTPUT);              /* BL_LED is "A29" */
	bl_print("my_app profile %s", pg_profile_name());
}

void loop(void)
{
	bl_write(BL_LED, BL_HIGH);
	bl_delay(500);
	bl_write(BL_LED, BL_LOW);
	bl_delay(500);
	bl_print("blink %d", ++count);
}
FunctionWhat it does
bl_pin_mode(pad, BL_OUTPUT)Make a pad an output, driven low. Returns 0, or -1 and prints why if the profile refuses it. Only outputs are supported
bl_write(pad, BL_HIGH|BL_LOW)Drive an output. Pads that were not accepted are ignored
bl_delay(ms)Wait about ms milliseconds, rounded up to the 5 ms tick
bl_print(fmt, ...)Print one line, same as pg_print()
bl_cmd_listen(id)Deliver a mailbox command id to bl_cmd_receive(). Call from setup()
bl_cmd_receive(&cmd, wait_ms)Wait up to wait_ms for a command. Returns 1 and fills cmd, or 0 on timeout. Counts as a delay for loop()
bl_cmd_reply(&cmd, value)Answer a command with a 31-bit value, exactly once and soon, because Linux waits 1 s by default

loop() must wait: call bl_delay() or bl_cmd_receive() with a non-zero time on every pass. A command receiver looks like this:

#include "beitlabduino.h"

#define CMD_LED 0x41

static int on;

void setup(void)
{
	bl_pin_mode(BL_LED, BL_OUTPUT);
	bl_cmd_listen(CMD_LED);
}

void loop(void)
{
	bl_cmd_t cmd;

	if (bl_cmd_receive(&cmd, 100)) {            /* wakes at once on a command */
		if (cmd.value > 1) {
			bl_cmd_reply(&cmd, BL_CMD_ERROR);   /* refuse bad values */
			return;
		}
		on = (int)cmd.value;
		bl_write(BL_LED, on ? BL_HIGH : BL_LOW);
		bl_cmd_reply(&cmd, (uint32_t)on);
	}
}

To enable another pad, add a profile manifest in the repository's profiles/ folder. An application pin entry records the owner, function, voltage, connector and purpose, with evidence from the schematic, the SDK mux and Linux ownership. A child profile cannot release a pin that Linux owns, and unknown pins are denied. See docs/PROFILES.md in the repository.

5. Pitfalls

Printing

pg_print() and bl_print() use the vendor formatter, not newlib's. It knows only %d %x %s %c %p and the l modifier. %x and %p always print every digit and widths are ignored. %u, %i and %f are not supported, and an unsupported letter does not end the conversion, so "period %u ms" reads its argument as a string pointer and crashes the C906. Use %d for values below 231 or %x, and cast to int.

  • The tick is 5 ms. vTaskDelay(pdMS_TO_TICKS(1)) and bl_delay(1) wait for the next tick and can be up to 5 ms short. Fast loops, like 10 kHz motor control, belong in an interrupt or a driver, not in task delays.
  • Memory. The program is an ELF64 for the C906 region 0x9fe00000 to 0xa0000000 (2 MiB). The builder checks this and an upload of an invalid ELF exits with code 2.
  • Shared GPIO registers. The A53 and the C906 share GPIO port registers, and FreeRTOS critical sections cannot synchronise with Linux. The driver preserves unrelated bits, but a cross-core race remains: verify timing-sensitive pin work on hardware.
  • Do not bypass the checked API. Direct SDK or memory-mapped register access skips the profile checks. Keep it out of programs you share.
  • One program at a time. An upload or recover replaces whatever the C906 is running. A new upload always stops the previous one.

Building without PlatformIO

PlatformIO calls firmware/rtosbuild.py, the same builder that compiles the starter firmware inside the image, so your program gets identical flags, start-up code and linker script. You can run it directly, for example in CI:

$ python3 firmware/rtosbuild.py build --profile duos_bare --name my_app \
    --out /tmp/my_app.elf my_app.c
$ python3 firmware/rtosbuild.py check /tmp/my_app.elf       # validate the ELF layout
$ python3 firmware/profiles.py beitlab_robotics_rev011        # inspect a profile

For a beitlabduino program add -I examples/platformio/common -I examples/platformio/common/lib/beitlabduino and list examples/platformio/common/lib/beitlabduino/beitlabduino.c among the sources, which is what the PlatformIO platform does for custom_libs. Upload the resulting ELF with python3 examples/platformio/common/upload.py /tmp/my_app.elf; it uses the same PIO_DUO_HOST settings.

Sharing your project

The goal of the SDK is to make C906 programs easy to share. A project is a folder with a platformio.ini and a src/ directory. To share one, publish that folder together with a note of the profile it requires, and ask people to drop it into examples/platformio/ of their own checkout.
