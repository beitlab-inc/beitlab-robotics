A Milk-V Duo S that makers can actually program

21 November 2026Beitlab Robotics

The Milk-V Duo S is a tiny board with two processors, Wi-Fi and a lot of promise. Getting it to do something useful in real time used to take an afternoon of SDK builds. We wrote a framework to make it take about forty minutes, and we are sharing it.

Share this article on LinkedIn Open the step-by-step guide

Why we built it

Our Balance Robot runs on a Duo S. The chip inside it, the SG2000, has a Linux core (a Cortex-A53) and a small real-time core (a C906). That is a great pairing for robots: Linux handles the network and the big software, and the small core does the timing-critical work without Linux getting in the way.

The catch is getting to that small core. The stock route means building the vendor SDK, learning its FreeRTOS tree, and reflashing the whole card every time you change a line of code. That is a lot to ask of someone who just wants to blink an LED or read a sensor.

So we built the missing piece, and we are calling it duo-s-playground.

What you get

Four things, and you do not need to build any of them yourself:

  • A ready-to-flash Linux image. It boots with Wi-Fi, SSH and a friendly network name, beitlab-milkv-duo.local.
  • A PlatformIO platform for the small core. You type pio run -t upload. Your program is built on your PC, sent over the network, and started on the C906.
  • beitlabduino. If you have ever used Arduino, you already know it: write setup() and loop() in plain C.
  • Examples and safety profiles. Working programs for blinking, mailbox commands and IMUs, plus profiles that stop your code from touching pins it should not.

Your first program in three steps

The whole path is written down in the SDK guide. Here is the short version.

  1. Write the card with your Wi-Fi already inside. The imager asks for your network name and password, finds your microSD card, writes it and checks the result. There is no serial cable and no typing on the board.
  2. Power it up. Set the boot switch to ARM, insert the card and power the board. About thirty seconds later it is on your network.
  3. Upload some code. Clone the repository, run its setup script once, pick an example and upload it.
git clone https://github.com/beitlab-inc/beitlab-os-milkv-duo-sdk.git duo-s-playground
cd duo-s-playground
python3 scripts/beitlab-imager.py --image ~/Downloads/beitlab-robotics-milkv-duo-os-0.4.1-duos-arm64-sd.img

scripts/fetch-freertos.sh
cd examples/platformio/hello
pio run -t upload
pio run -t rtmonitor

The last command shows a line from the board once a second. That line is your program, running on the small core, while Linux stays up and your SSH session stays open.

Write code the way you like

You can write in two styles. They build and upload the same way, so you can start with one and move to the other.

Arduino style

This is a complete blink program for the on-board LED:

#include "beitlabduino.h"

void setup(void)
{
	bl_pin_mode(BL_LED, BL_OUTPUT);
}

void loop(void)
{
	bl_write(BL_LED, BL_HIGH);
	bl_delay(500);
	bl_write(BL_LED, BL_LOW);
	bl_delay(500);
}

Plain C with FreeRTOS

If you want several tasks, queues or your own timing, skip the layer and write FreeRTOS tasks directly. You create them in one function and the runtime does the rest:

void playground_app_init(void)
{
	xTaskCreate(blink_task, "blink", configMINIMAL_STACK_SIZE, NULL,
		    tskIDLE_PRIORITY + 1, NULL);
}

Both styles can also receive small commands from Linux through a mailbox. That lets a Python script or a ROS 2 node on the board tell the real-time core what to do, which is exactly how our robot is wired. The write-your-own guide has templates for both.

Made for the board, safe for the robot

A real-time core with direct access to pins is powerful, and it is also easy to misuse. A wrong pin on a motor board is not a typo, it is a spinning wheel.

That is why every project picks a hardware profile. The profile for the Robotics Board allows only the on-board LED and refuses everything the robot owns. The profile for a bare Duo S allows the header pins that are verified for that board. If your code asks for a pin the profile does not allow, it is refused and tells you why, instead of quietly doing something you did not mean.

It works the same way on both platforms:

  • The Robotics Board. The Duo S sits on our carrier with motor drivers, an IMU and a latched E-stop.
  • A standalone Duo S. Just the board, a USB-C cable and whatever you wire to its header.

The examples page compares the two and lists every example with what you should see.

Where it stands

We would rather be clear than impressive, so here is the honest state of things. The image, the tools and the examples build and pass their checks. The Wi-Fi setup is automated and tested on real card images, and a fresh-card run on hardware is still on our list. The IMU example builds, but its physical readings are still waiting for hardware qualification. Flashing from macOS is supported, but it has not been validated on a physical card yet, and the C906 toolchain needs Linux, or WSL2 on Windows.

If you try it and something does not match these pages, we want to know.
